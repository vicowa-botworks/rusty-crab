# rusty-crab

A Rust port of [picoclaw](https://github.com/vicowa-botworks/picoclaw), an
assistant runtime that lives in messaging channels.

This repository is a **port, not a rewrite**. picoclaw's Go implementation is the
specification, and it stays the specification: the observable behaviour here is
required to match it value for value, including the parts that look accidental.
Where the two disagree, this repository is wrong until proven otherwise — and
"proven otherwise" means a deliberate, recorded decision to diverge, never a test
that was easier to change than the code.

## Why it is pinned rather than reimplemented

picoclaw keeps state on disk that users already have: memory-store JSONL, session
files, configuration. Those formats are not negotiable — a port that "improves"
one of them strands every existing install.

The subtler constraint is behavioural. `pkg/tokenizer`, for instance, estimates
token counts to decide when a conversation gets compacted. A port that produces a
slightly different estimate does not crash; it compacts at a different moment, so
different turns survive, so the assistant answers differently. Nothing fails and
nobody notices. That class of drift is the reason this repository is built around
a conformance oracle instead of around review.

## How correctness is established

`conformance/` holds fixtures generated by **the Go code itself** — `cmd/oracle`
in picoclaw calls the real functions over an adversarial corpus and records
`(input, expected)` pairs. The Rust tests replay them.

So a green suite means "this Rust code agrees with what the Go code does", not
"this Rust code agrees with what someone believed the Go code does". The
difference is the whole point: building the port from the fixtures has already
caught four behaviours that reading the Go source did not suggest (see
[Porting hazards](#porting-hazards-found-by-the-oracle)).

```sh
cargo test          # unit tests + the full conformance replay
```

Regenerating the corpus, and what to do when a fixture fails, is
[`conformance/README.md`](conformance/README.md).

## Layout

| Path | What it is |
|---|---|
| `crates/crab-tokenizer` | Token-count estimation (`picoclaw/pkg/tokenizer`) |
| `crates/crab-gojson` | A byte-exact re-implementation of Go's `encoding/json`, for the values the port reaches |
| `conformance` | The fixture harness and the committed fixtures |
| `docs/ARCHITECTURE.md` | The Go package graph, the port order, and the layering rules the port must not break |

## Porting hazards found by the oracle

Recorded here because each one cost a debugging cycle and none of them are
visible from the Go source:

- **`encoding/json` escapes `<`, `>` and `&`.** Go's encoder does this by default;
  `serde_json` does not. Since the tokenizer measures `len(json.Marshal(x))`, the
  escaped form is three times longer and the estimate differs.
- **Negative exponents lose a leading zero, positive ones keep theirs.**
  `strconv` writes `1e-07`; `json.Marshal` post-processes it to `1e-7`. `1e+21` is
  untouched. A port that formats via `{:e}` plus padding is one byte short on
  every small float.
- **`\b` and `\f` have short escapes.** JSON allows them raw, so a writer that
  handles only `\n \r \t` emits six bytes where Go emits two.
- **`serde_json`'s default number parsing is not correctly rounded.** It
  accumulates decimal digits into an `f64` and lands one ULP away on some
  shortest-round-trip literals. With the feature off, 27 of 676 encoded parameter
  values mismatched — the harness mis-parsing the fixture, not the port encoding
  wrongly. `arbitrary_precision` is required, and not only for tests: any code
  here that reads provider JSON into an `f64` will otherwise disagree with Go
  about which number it has.

## Ground rules for work here

1. **A conformance failure is a bug in this repository or a stale fixture — never
   a test to relax.** Establish which side moved first, then fix that one.
2. **No behaviour change without a recorded divergence.** If this port must differ
   from Go, say so in `docs/DIVERGENCES.md` with the reason, and expect to be
   asked why.
3. **Format-compatible surfaces stay format-compatible.** Memory JSONL, session
   files and config serialization keep their field names, ordering and defaults.
4. **Port in dependency order.** `docs/ARCHITECTURE.md` has the graph; a crate
   whose dependencies are not ported yet is a crate that will be guessed at.
